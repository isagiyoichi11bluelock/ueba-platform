# UEBA Platform — Known Limitations

This document is an honest account of what the UEBA Platform **cannot** do, what assumptions it relies on, and where it may fail in practice.  Transparency about limitations is as important as demonstrating capabilities.

---

## Synthetic Data Limitations

### 1. Simulated Realism
The synthetic dataset is generated by a seeded random process following parameterised distributions.  Real-world event logs are messier:
- Clock skew and timestamp normalisation issues
- Missing fields (e.g. absent `device_id` for BYOD)
- Duplicate events from retry storms
- Encoding inconsistencies in country/city names

The generator does not model these failure modes.

### 2. Static Organisation
The synthetic org has a fixed structure for the full 90-day window.  Real organisations experience promotions, transfers, acquisitions, and mass onboarding that significantly complicate baselines.

### 3. Known Ground Truth
Scenarios are injected with exact labels, making evaluation artificially clean.  Real detection requires human analysts to validate every positive — there is no `scenario_labels.csv` in production.

---

## Detection Limitations

### 4. No Zero-Day Scenarios
The indicator set covers known threat patterns.  Novel attack methods not represented in the 15 indicators will produce low or zero scores.  The ML signal provides partial coverage but is not a substitute for scenario-driven indicator design.

### 5. Single-Session Scope
Indicators are computed per user-day.  Low-and-slow attacks spread across multiple weeks may accumulate individually sub-threshold scores that never breach an alert band.  A weekly aggregation mode is not yet implemented.

### 6. No Network Lateral Movement
The platform models access to named resources but not network-level lateral movement (e.g. port scanning, ARP spoofing, Kerberoasting).  UEBA complements but does not replace network detection tools (NDR/IDS).

### 7. Geographic Accuracy
IP-to-geography mapping is approximated.  VPN exit nodes, Tor, cloud NAT, and corporate proxies can all produce incorrect country/city attributions, leading to both false positives (e.g. innocent VPN use flagged as NEW_COUNTRY) and false negatives (attacker using a domestic exit node).

### 8. Peer Group Size
With only 60 users across 5 departments, peer groups may contain as few as 8–12 people.  Small peer groups make peer-deviation statistics unreliable.  Production UEBA requires hundreds of users per role for robust peer analytics.

---

## Scoring and Calibration Limitations

### 9. Uncalibrated Weights
Indicator base points and chain bonuses in `scoring_weights.yaml` are set by design intuition, not empirical calibration on historical incident data.  In production, weights should be calibrated using labelled historical alerts and tuned to the organisation's risk appetite.

### 10. No Temporal Decay
All hits in a user-day are weighted equally regardless of how long ago the behaviour occurred within that day.  A single 3am login should arguably carry more weight than the same login at 10pm.

### 11. Context Dampening Is Binary
A signal is either active or not.  In reality, a "project deadline" should dampen proportionally to how close the deadline is — but the current model applies the same factor whether the deadline is tomorrow or in 2 weeks.

## Operational Limitations

### 12. SQLite Scalability
SQLite is not suitable for concurrent write workloads or organisations with more than ~1M events/day.  A production deployment would require PostgreSQL or a time-series database (e.g. TimescaleDB, ClickHouse).

### 13. No Real-Time Streaming
The pipeline is batch-oriented (run once per day).  Real UEBA requires near-real-time processing for high-severity indicators like IMPOSSIBLE_TRAVEL or FAILED_LOGIN_BURST_THEN_SUCCESS.  An Apache Kafka + Flink or Spark Streaming architecture would be appropriate at scale.

### 14. No Integration with HR Systems
Context signals (travel approvals, role changes, departures) are synthetic.  Real integration requires connectors to HR/ITSM systems (Workday, ServiceNow), which introduce data-quality and latency challenges.

### 15. Single-Tenant Only
The current architecture supports one organisation's data in one SQLite file.  Multi-tenancy, data isolation, and per-tenant key management are not implemented.

---

## ML Model Limitations

### 16. Concept Drift
The Isolation Forest is trained on a static 75-day baseline.  In production, organisational behaviour evolves (new products, acquisitions, remote-work shifts), causing the model to drift.  Regular retraining and drift monitoring are required.

### 17. No Explainability for ML Signal
Isolation Forest does not natively provide feature-level explanations.  The ML_ANOMALY_SUPPORT indicator is intentionally capped at 15 points and treated as supporting signal only for this reason.

### 18. Contamination Parameter
The `contamination=0.05` default assumes 5% of baseline events are anomalous.  This is a hyperparameter that significantly affects sensitivity and must be tuned per organisation.

---

## Privacy Limitations

### 19. Salt as Single Point of Failure
The pseudonymisation salt is stored in `.env`.  Compromise of this file allows re-identification of all pseudonyms.  Production systems should use an HSM or secrets manager.

### 20. No Differential Privacy
Aggregate statistics (e.g. department download volume) may leak individual information when groups are small.  Differential privacy noise injection is not implemented.
